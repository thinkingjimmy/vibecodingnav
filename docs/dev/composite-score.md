# 场景综合评分（0–100）设计

> 数据：`thinkingjimmy/vibecodingnav` main 分支，2026-10-11 读取 `src/content/boards/*.json` 与 `src/content/results.ts`（Next.js Evals、ReactBench 只取基线臂）。脚本：`composite/composite.py`（三种方法）、`composite/sensitivity.py`（稳健性）、`composite/tables.py`（生成下表）。本文只做设计，不改站点代码。

## 1. 现在的问题

首页卡片按「模型出现过的榜的平均名次」排序（`catalog.ts › fuseScenario`）：

| 模型 | WebDev | 图生网页 | Next.js | ReactBench | 平均名次 |
|---|---|---|---|---|---|
| Claude Opus 5.5 | #1 | #1 | #1 | — | 1 |
| Claude Sonnet 5.5 | #3 | #2 | — | — | 2.5 |
| Claude Fable 5.1 | #5 | #4 | #3 | #1 | 3.3 |
| GPT-6 Astra | #2 | #3 | #7 | — | 4 |
| GPT-6.1 Sol | #4 | #5 | — | — | 4.5 |

四个毛病：
1. **缺榜反而占便宜**：Sonnet 5.5 只上了两张最强的榜，平均名次就排到第二；Fable 5.1 四张都上，反而被拉低。
2. **名次不分榜大小**：Next.js 只有 14 行，#7 已经在后半段；WebDev 有 142 行，#7 还在前 5%。现在两者等价。
3. **名次丢掉了分差**：WebDev 第 1 和第 2 差 27 分，第 3 和第 4 差 19 分；Next.js 前三同为 97%。名次把“几乎一样”和“差很多”说成同一件事。
4. **所有榜一样重**：主榜（85 万票盲评）和第三方生态评测、框架厂商出题的评测权重相同。

另外，`boards/README.md` 与 ReactBench 页面目前写着“不把不同评测合成一个数”。采用综合分需要同步改这条规则：**综合分只用于排序和首页摘要，场景页的融合表仍逐格显示原始名次和分数，不替代原榜。**

## 2. 设计目标
- **公平**：缺榜不占便宜，也不一票否决；不同大小的榜可比。
- **可解释**：一句话说得清；每个格子都能还原到原榜一行。
- **稳健**：权重在合理范围内变动时，前 5 名不变；新增一个冷门模型不会改变别人的分数。

## 3. 关键选择

### 3.1 单榜归一化：三种做法

| 做法 | 公式 | 优点 | 问题 |
|---|---|---|---|
| 名次百分位 | (N − 名次) / (N − 1) | 简单，不看量纲 | **依赖榜单收录了多少旧模型**：WebDev 收 142 行，第 9 名仍有 94 分；Android 只有 10 行，第 9 名只有 11 分。丢掉分差。 |
| z 分数（→ 正态百分位） | Φ((x − 均值) / 标准差) | 用到分差 | **均值和标准差被榜尾的旧模型左右**；同分不同榜可比性差；Next.js 接近天花板时，第 7 名 90% 被压到 68。 |
| **相对榜首** | 竞技场榜：2 × 对榜首的预期胜率；通过率榜：通过率 ÷ 榜首通过率 | **只看与最强者的距离，不受榜尾影响**；竞技场分换成胜率有直观含义（落后 100 分 ≈ 胜率 36% → 72 分）；接近天花板的榜自动区分度低，不会放大噪音 | 依赖榜首一个点；竞技场与通过率两种换算的“陡度”不同（需要用权重平衡） |

竞技场换算：LMArena 的 Bradley-Terry 分与 Elo 同量纲，对榜首胜率 p = 1 / (1 + 10^((榜首 − x)/400))，归一化 = 200p，榜首 = 100。

### 3.2 缺榜处理
- **忽略**（现状）：只上强榜的模型占便宜。
- **按 0 分**：等于惩罚“评测方没测”，对新模型不公平。
- **贝叶斯收缩（推荐）**：缺的那张榜，按“该榜模型的中位水平”补一个**半权重**的先验观测。上过的榜越多，先验影响越小；完全没上某张次要榜，只会被轻微拉向中等水平。当前各榜先验（中位归一化分，四榜时期）：WebDev 52、图生网页 60、Next.js 87、ReactBench 69；sudo L7 为通过率榜，缺榜同样按该榜中位半权收缩。

规则化写法：主榜 1.0；独立第三方同类评测 0.6；厂商自评 / 生态评测 0.4；单个模型厂商自报的成绩不进综合分。`specific` 基准最多一个场景；`general` 可跨场景。

### 3.4 不确定性
- 标“初步”（Preliminary）的行，该格权重减半。
- 不把 CI 直接折进分数（解释成本高），而是在展示层处理：**综合分相差 < 3 视为接近**，卡片可以并列显示或加“≈”。
- 并列：四舍五入到整数后同分即并列名次（如 sudo L7 的 Opus 5.5 与 Sonnet 5.5 都是 45.0 → 都是 100、并列第 1）；展示顺序再按主榜名次。

### 3.5 上首页的门槛
- 必须出现在**场景主榜**。
- 已观测榜单的权重 ≥ 总权重的 50%（Web 前端即 ≥ 1.8 / 3.6；Android 即 ≥ 1.1 / 2.2；CLI 即 ≥ 0.8 / 1.6）。Gemini 4 Argon 只上了 WebDev，留在场景页，不上首页卡片。
- 有模型页（有 `modelSlug`）。

## 4. 三种候选方法

- **A 名次百分位 · 等权 · 忽略缺失**：把现状的平均名次换成百分位。
- **B z 分数 · 加权 · 缺榜补 50（全权重）**。
- **C 相对榜首 · 加权 · 向中位收缩（推荐）**：

```
综合分 = Σ_已上榜 w_b · s_b  +  Σ_缺榜 0.5 · w_b · m_b
        ──────────────────────────────────────────────
              Σ_已上榜 w_b  +  Σ_缺榜 0.5 · w_b
s_b = 该模型在榜 b 上相对榜首的水平（0–100），m_b = 榜 b 的中位水平
```

单榜场景（CLI）没有缺榜问题，C 就是“通过率 ÷ 榜首通过率”，排序与原榜一致，只改变分数的刻度。Android 现为双榜（主榜 + sudo L7），缺 sudo 的模型按中位半权收缩。

## 6. 推荐：方法 C

**理由**：
1. 相对榜首不受榜单收录了多少旧模型影响，142 行和 14 行的榜可以放在一起；
2. 缺榜按半权重向中位收缩，既不占便宜也不一票否决，上的榜越多越可信；
3. 主榜决定大局，次要榜只做修正，权重变动时前 5 名成员不变；
4. 每个数都能还原：格子里的 s_b 直接由原榜一行算出。

**站点上的一句话说明**（卡片底部 / 悬停提示）：

> 综合分（0–100）：每张榜按与榜首的差距换算，榜首记 100；主榜权重最高，没参加的榜按中等水平折半计入。

英文：*Composite (0–100): each board is scored against its leader (leader = 100). The primary board weighs most; boards a model skipped count at half weight as a median result.*

## 7. 落地建议（给实现者）
- 在 `Benchmark` 上加 `compositeKind: "arena" | "rate"` 与场景 `boards[].weight`；`fuseScenario` 产出 `composite`、`coverage`、每格 `s_b`，排序改用 `composite`。
- 综合分只用于排序和首页卡片；场景页融合表仍逐格显示原始名次与分数，表头加“综合”一列并附上面那句说明。
- 每次同步榜单后跑一次稳健性检查；若前 5 成员在 27 组扰动下发生变化，在「最新变化」里说明。
