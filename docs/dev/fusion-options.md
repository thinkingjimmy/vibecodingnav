# “模型 + Skill + 框架”组合：IA 方案对比

> 背景：用户的真实问题往往是“我要做前端，用什么？”，答案横跨三类实体：模型（来自场景榜单）、Skill / 插件 / Prompt、库与框架（来自工具箱）。下面四种方案是把这个“组合”放进 IA 的不同办法。

## 方案 1 · 配方（Stack）作为第三种顶层内容
- **导航 / URL**：顶栏加「配方」，`/stacks`、`/stacks/nextjs-shadcn-landing`；一个场景下可以有多份配方（如“落地页配方”“后台面板配方”）。
- **首页**：加一排热门配方。
- **优点**：粒度最细，可分享、利于长尾 SEO；后续可开放社区投稿。
- **缺点**：和场景页概念重叠（用户分不清“场景”和“配方”）；数量一多就难以维护和保持新鲜。
- **维护成本**：高。每份配方都要单独跟进模型榜单和库的版本。

## 方案 2 · 在场景页顶部嵌一个「推荐组合」区块
- **导航 / URL**：不变，组合挂在 `/scenarios/web-frontend#stack`。
- **首页**：不变。
- **优点**：最便宜，零新增页面类型；证据（榜单）就在下面。
- **缺点**：场景页已定位为“榜单”，组合会把它变成两件事；无法给“做 X”单独做 SEO、分享与导出；没有榜单的场景（iOS）也很尴尬。
- **维护成本**：低。

## 方案 3 · 任务落地页「做 X」，位于场景与工具之上（推荐）
- **导航 / URL**：顶栏加「组合」，`/build`、`/build/web-frontend`（中文 `/zh/build/web-frontend`）。与场景一一对应的 slug，初期 6 个。
- **页面**：角色表（模型 / Skill / UI 组件 / 图标 / 动效 / 字体 / 设计稿）× 首选 + 备选；「带走这一套」导出 AGENTS.md 和安装命令；「这一套不适合」；「依据」链接回场景榜单和各工具详情页。
- **首页**：Hero 下一行“直接开工：做 Web 前端 · 做一个 Android App …”；场景页顶部一条「推荐组合」入口链接到这里（吸收方案 2 的优点）。
- **优点**：直接回答“我要做 X 用什么”；场景页保持纯榜单，工具箱保持纯目录，组合页只做**引用**，不重复内容；天然适合 SEO（“用 AI 做前端 用什么”）和分享；导出 AGENTS.md 是方案 4 的种子。
- **缺点**：多一种页面类型；需要编辑为每个任务写取舍说明。
- **维护成本**：中低。模型行自动取场景榜单的首选/省钱/开源三档（构建时计算），工具行引用工具实体；编辑只维护“角色 → 条目”的映射和几句理由。榜单变化时组合页自动更新并进入「最新变化」。

## 方案 4 · 用户自选的 Stack Builder，导出 AGENTS.md
- **导航 / URL**：顶栏加「搭配」，`/builder?model=…&skill=…&ui=…`（状态存在 URL 里，可分享）。
- **首页**：一个“开始搭配”入口。
- **优点**：最灵活、最有“工具感”；导出文件让网站进入用户的工作流。
- **缺点**：静态站要做较多客户端逻辑；空白画布对新手不友好（需要默认值，也就是方案 3 的内容）；SEO 价值低。
- **维护成本**：开发成本高，内容成本低（复用实体数据）。

## 推荐
**先做方案 3，并把方案 2 退化成场景页顶部的一条入口链接；方案 4 作为方案 3 页面上的“改一项再导出”功能，后续迭代。**
理由：它让三类实体各司其职（场景 = 证据，工具箱 = 目录，组合 = 结论），组合页只引用不复制，维护量可控；同时第一时间回答用户最想问的问题。

| | 新页面类型 | 用户理解成本 | SEO / 分享 | 维护 | 开发 |
|---|---|---|---|---|---|
| 1 配方 | 有，数量多 | 中（与场景重叠） | 高 | 高 | 低 |
| 2 场景内嵌 | 无 | 低 | 低 | 低 | 低 |
| **3 做 X 任务页** | 有，与场景 1:1 | 低 | 高 | 中低 | 低 |
| 4 Builder | 有，1 个 | 中高 | 低 | 低 | 高 |
